# LargeIntegers: keeping the C in sync with the class

`src/common/LargeIntegers.c` is checked in, but it is derived from
`smalltalksrc/VMMaker/LargeIntegersPlugin.class.st`. `sync-c.sh` derives it again and either
writes it or, with `--check`, reports whether the checked-in file is still exactly what the class
generates. The multiply and divide kernels (`src/common/LargeIntegersKernels.c`,
`include/common/LargeIntegersKernels.h`) are hand-written C, and these tools do not touch them.

| file | what it does |
|---|---|
| `sync-c.sh` | translates the class with Pharo Slang in a temporary copy of a VMMaker image, runs `convert.py`, then writes the C or compares it with the checked-in file |
| `regen.st` | the script the image runs: it loads the Slang packages of the tree's `smalltalksrc` with Monticello and translates `LargeIntegersPlugin` the way `PharoVMMaker` does |
| `convert.py` | converts the Slang output to the checked-in conventions (see below) |

## Running it

```
PHARO_VM=<vm> plugins/LargeIntegers/tools/sync-c.sh [--check | --digests] [--keep] <VMMaker.image> [<repo root>]
```

- `<VMMaker.image>` is the image that `cmake/vmmaker.cmake` builds (target `vmmaker`), for
  example `<build>/build/vmmaker/image/VMMaker.image`. Its `.changes` file and the `.sources`
  file next to it are copied too. The image itself is never written.
- `PHARO_VM` is the VM that runs the image: either the `pharo` executable or the directory that
  holds it. When it is unset, the script uses the VM that cmake downloads next to the image
  (`<build>/build/vmmaker/vm`).
- `<repo root>` defaults to the repository the script lives in. The `.st` is read from
  `<repo root>/smalltalksrc`, and the C is written to `<repo root>/plugins/LargeIntegers/src/common/`.
- `--check` writes nothing. It exits 1 on drift and prints the first 100 lines of the diff.
- `--digests` writes nothing. It prints the digests that pin the C taken from the checked-in file
  (see "Kept verbatim" below), as the `VERBATIM` and `VARIABLES` tables of `convert.py`.
- `--keep` keeps the temporary directory (about 300 KB), which holds `regen.log`, the raw Slang
  output `regen/LargeIntegers.c` and, when the conversion got that far, the converted `out.c`.
  There is no `out.c` after a stop on a pinned digest (exit 1 without a diff) or a failure
  (exit 3). The copy of the image, its `.changes` and `.sources`, and the `pharo-local` it
  writes (about 130 MB together) are deleted even with `--keep`.
- `PYTHON` (default `python3`) and `TMPDIR` can also be set.

Exit status:

| status | meaning |
|---|---|
| 0 | the C agrees with the class, or was written |
| 1 | drift (with `--check`), or C taken from the checked-in file no longer matches its pinned digest: the class changed it, or it was edited by hand (see "Kept verbatim" below) |
| 2 | usage or environment error |
| 3 | the `.st` failed to load or to translate, and the `LISYNC-ERROR` lines name the method; or `convert.py` stopped on an input it does not understand (its message says what) |

A run takes about 10 s, most of it spent loading the packages. It needs a POSIX shell, `python3`
(standard library only) and the VM. It works from any directory.

## Editing the plugin

1. Edit `LargeIntegersPlugin.class.st`.
2. Run `sync-c.sh <VMMaker.image>`. It rewrites `src/common/LargeIntegers.c` and reports each
   rule that changed something: a new function, a method comment taken from the class, a dropped
   statement comment. When it stops with exit 1 on a pinned part, see "Kept verbatim" below.
3. Build: `cmake --build <build> --target LargeIntegers`. A build directory configured before
   `LargeIntegersKernels.c` existed must re-run cmake, because the plugin sources are a glob.
4. Test with `sh ../tests/run-c-tests.sh`, which runs the C-level tests (no VM needed), and
   `sh ../tests/run-image-tests.sh <vm-dir> <image>`, which drives the plugin of a built VM from
   an image. See `../tests` for both.
5. Commit the `.st` and the `.c` together, with `convert.py` if its digests were refreshed.
   `sync-c.sh --check` should then print `AGREE`.

Do not edit the C by hand, except to follow a change of the class in the parts the conversion
takes from the checked-in file (listed below). A hand edit elsewhere is overwritten by the next
sync, and `--check` reports it as drift until then. A hand edit of a pinned part (the eight
verbatim functions and the Variables section) makes the sync stop with exit 1 until its digest
is refreshed. The header comment and the comments between functions are not checked.

## Why the checked-in C is not the plain generator output

The file was first generated by the Squeak `SmartSyntaxPluginCodeGenerator`
(VMMaker.oscog-eem.2495). The Pharo Slang of this tree generates different text, and some of it
cannot be used as is:

- It leaves the SmartSyntax return conversions untranslated, as `asOop(x, _SmallInteger)` and
  `asOop(x, _Boolean)`.
- After a failed receiver check, its primitive prologs do `popthenPush(n, null)` before
  returning.
- It emits `debugCode(msg(...))`, and `msg` is a debugging function.
- It emits a standalone static copy of every inlined method.

Its layout also differs from the old generator's: `_` prefixes on locals, `/* end ... */`
markers, `} else {`, braces around `remapOop:in:` blocks, an unused `v` local for
`addressOf:put: [:v | ...]`, method comments laid out differently, and statement comments
dropped. The first rewrite of the plugin kept the old file's layout so that the diff showed only
real changes. `convert.py` reproduces that layout mechanically:

- **Function bodies** are Pharo Slang's, with these changes:
  - `asOop:` is translated to `integerObjectOf()` or `(x ? trueObject() : falseObject())`.
  - The `_` prefixes, `/* end */` markers, `remapOop:in:` braces and the `v` local are dropped.
  - `debugCode(...)` becomes `/* missing DebugCode */;`, as in the old output.
  - `} else {` is split onto two lines.
- **Primitive prologs.** The statements before `debugCode` are the parameter fetches, the arity
  check and the hand-written argument checks of the `.st`. In them, the out-parameter
  initialisations `x = 0;` are dropped and `&&` is wrapped as the old generator wrapped it. The
  `popthenPush(n, null)` of the failed receiver check is dropped.
  The `.st` declares every argument `#Oop` and checks it by hand after the arity check, because
  SmartSyntax runs its typed-argument validation before the method body. That validation
  dereferences stack slots above the real arguments when the call has too few.
- **Functions kept.** Only the functions reachable from the exports are kept, so the standalone
  copies of inlined methods disappear. Functions keep their order in the checked-in file. A new
  function is placed where Slang emits it.
- **Kept verbatim.** Eight functions keep the old generator's text, because no rule produces it
  (casts, `?:` layout, an `int` local, the guarded proxy imports of `setInterpreter`):
  `cDigitHighBitlen`, `cDigitOfat`, `cHighBit32`, `largeIntgrowTo`, `normalizeNegative`,
  `normalizePositive`, `primDigitCompare` and `setInterpreter`. The Variables section, from
  `/*** Variables ***/` to the first function, is also the checked-in one: it holds the class's
  constants (`declareCVarsIn:`), its variables, the module name and version, and the
  `interpreterProxy` imports. This C is equivalent to the class, but nothing derives it from it.
  Instead, `VERBATIM` and `VARIABLES` in `convert.py` pin each part with two digests: one of its
  converted Slang output, one of its checked-in text.
  - If an edit of the class changes that output, which includes a change to a method inlined
    into one of the functions, or to a constant, a variable or `version`, `sync-c.sh` stops with
    exit 1, names the part and says "the class changed it".
  - If the checked-in text was edited, it stops with exit 1 and says "its checked-in C was
    edited". Undo the edit, unless it follows a change of the class.
  - To fix a change of the class, either update that C by hand or, for a function, remove it
    from `VERBATIM` to take the generated text. `--keep` keeps the raw Slang output to compare
    with. Then run `sync-c.sh --digests <VMMaker.image>` and paste its output over `VERBATIM`
    and `VARIABLES` in `convert.py`.
- **Taken from the checked-in file:**
  - the header comment and `__buildInfo`;
  - the Variables section (pinned, see above);
  - the text between functions, which is mostly method comments.

  The old generator also left there the comments of inlined methods, and the conversion keeps
  them. A method comment that differs from the class's, ignoring white space and comment
  delimiters, is replaced by the class's.
- **Taken from the Slang output:** the includes, the `#define` constants, the export table and
  the accessor depths. The prototypes are rebuilt from the functions.
- **Statement comments.** Pharo Slang drops comments inside method bodies. A comment block of the
  checked-in C is kept in front of the statement it annotates, as long as that statement line is
  still generated.

## Known limits

- **Variables and proxy imports.** The Variables section and `setInterpreter` are not
  regenerated. Any change of them in the class, a new constant, variable, module version or
  `interpreterProxy` import, stops the conversion with exit 1 (their pinned digests change).
  `convert.py` also checks that every proxy function called is imported, which covers the
  imports its own `asOop:` translation needs. Update the C by hand, then refresh the digests.
- **Not checked.** The header comment, `__buildInfo` and the comments between functions come from
  the checked-in file and are not pinned: a hand edit of them is kept without a message.
- **Method comments.**
  - A method comment that Slang does not emit is never updated. This covers the comments of
    inlined methods, and of `cDigitRshift:from:len:to:len:`.
  - When a function disappears, the comments in front of it go with it.
- **Statement comments.** A statement comment whose line changes is dropped, with a message. If
  you still want it, put it back by hand after the sync. It is then carried over from the next
  sync on.
- **Translation target.** The translation is the 64-bit Spur CoInterpreter one, as `PharoVMMaker`
  does it. The C is the same for every target, which differ only in `#if BytesPerOop`.
- **Where it was tested.** It was tested on Linux x86_64, under dash and Python 3.12, with the
  VMMaker image (Pharo 13) that cmake builds, run by this tree's VM. The output depends only on
  the tree's `smalltalksrc`, which `regen.st` loads over the image's code, and on the image's
  Pharo base.
